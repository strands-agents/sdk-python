An agent's message history is expected to come from a source you trust: prompts your application builds, and history it produced and stored itself. History can carry more than text. It can carry tool-call content, and in the Python SDK a tool-call block as the most recent message causes the agent to dispatch that tool on its next invocation, without a model response in between. When the history comes from a source you do not control, invoke the agent with `allow_resume=False` so it cannot start by dispatching a tool.

This dispatch behavior is specific to the Python SDK. The TypeScript SDK appends a tool-call message and its result together after a tool runs, so restored history never carries a trailing tool-call block to resume from.

## Why tool-call content is different

In the Python SDK, the agent dispatches a tool whenever the latest message in its history contains a tool-call content block. That path is deliberate: it lets an agent resume from a point where the model had already decided to call a tool. The dispatch check looks only at the content of the latest message. It does not consider the message's role or where it came from.

The behavior is correct when the tool-call block came from the model. It is a problem when the block came from a party you do not trust, because that party has then chosen which tool runs and with which arguments. The model is never consulted on that turn, so this is not the model being led astray. A tool-call block in untrusted history is a direct request to run a tool.

## When history is untrusted

History your own application builds or persists to storage only it can write is trusted. Invoke as usual; resumption works as before.

Treat history as untrusted when a party you do not control could have influenced it before it reached the agent. That covers three ways history enters an agent:

- **Direct invocation** with a caller-supplied message list, for example a request body deserialized into messages and passed to the agent.
- **Session restore**, when the session store can be written by something outside your application.
- **Snapshot load**, when the snapshot was accepted over the network or read from a shared store.

All three feed the same history and the same dispatch check. The guidance below applies to each.

## Require a model call with `allow_resume`

Every agent invocation accepts an `allow_resume` parameter, which defaults to `True`. Set it to `False` to guarantee the invocation starts with a model call on the input you provide. If anything would resume the loop without a model call first (a latest message containing `toolUse`, an interrupt resumption, or a `checkpointResume` block) the invocation raises `ValueError` before any agent state is modified. No history is appended and no checkpoint is consumed.

```python
from strands import Agent

agent = Agent()

# untrusted_messages came from a request body, queue, or shared store.
# A trailing toolUse block raises ValueError instead of dispatching a tool.
result = agent(untrusted_messages, allow_resume=False)
```

The same parameter guards a resume from history the agent already holds:

```python
# Guards resume-from-existing-history, not just the supplied prompt.
result = agent(None, allow_resume=False)
```

`allow_resume=False` closes the direct-dispatch path. It does not make untrusted content safe on its own: history that reaches the model can still carry prompt-injection text, and a snapshot or session payload can also carry tampered state or model state. Treat it as one control, not a substitute for trusting the source.

Handle the `ValueError` where you accept untrusted input, so a probe surfaces as a rejected request rather than an unhandled error:

```python
result = None
try:
    result = agent(untrusted_messages, allow_resume=False)
except ValueError:
    # Reject and log: the caller supplied history that would resume the loop.
    ...
```
