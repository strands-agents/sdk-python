Plugins like [Context Offloader](./plugins/context-offloader.mdx)
and [Session Management](./agents/session-management.mdx) need
somewhere to persist data — offloaded tool results, conversation
snapshots, agent state. `Storage` is the minimal interface they
write to: four async methods over raw bytes, keyed by opaque
strings.

You choose the backend once and hand it to the plugins that need
it. The SDK ships three built-in backends (in-memory, local
filesystem, and Amazon S3), or you can implement your own.

## The interface

All Storage implementations share the same contract:

| Method | Description |
| --- | --- |
| <Syntax py="write(key, data)" ts="write(key, data)" /> | Store bytes under `key`, overwriting if it exists |
| <Syntax py="read(key)" ts="read(key)" /> | Return the stored bytes, or `None`/`null` if missing |
| <Syntax py="delete(key)" ts="delete(key)" /> | Delete the value. No-op if the key does not exist |
| <Syntax py="list(query)" ts="list(query)" /> | List keys matching a prefix, sorted ascending |

Keys are opaque strings — the interface imposes no format. The
shipped backends (InMemoryStorage, LocalFileStorage, S3Storage)
use `/`-separated path-like keys and normalize them (collapsing
repeated slashes, stripping leading/trailing slashes, rejecting
`..` segments), but custom backends may use any key format they
choose.

All methods are async. Data is raw bytes (`bytes` in Python,
`Uint8Array` in TypeScript) with no content-type or metadata
attached — consumers handle serialization themselves.

  knowledge and retrieval data across conversations

## Built-in backends

Choose a backend based on your durability and deployment needs:

| Backend | Persistence | Best for |
|---------|-------------|----------|
| `InMemoryStorage` | Process lifetime only | Testing, serverless, short-lived agents |
| `LocalFileStorage` | Local disk | Development, debugging, single-machine deployments |
| `S3Storage` | Amazon S3 | Production, shared state across instances |

### LocalFileStorage

Persists each key as a file under a base directory (default
`./.strands/`). Key segments map to directory segments — a key
like `session/abc/state.json` becomes the file
`.strands/session/abc/state.json`. Writes are atomic on the host
filesystem (write to a temp file, then rename).

## Keys and namespacing

The shipped backends use `/`-separated keys. Plugins auto-scope
their keys to avoid collisions — Context Offloader writes under
`offloader/`, Session Manager writes under `session/`. You don't
need to include these prefixes yourself.

The SDK provides a `namespace()` helper that prepends a
`/`-separated prefix to every key transparently. This is a
convenience for the shipped path-based backends — custom backends
with a different key scheme can implement their own namespacing:
